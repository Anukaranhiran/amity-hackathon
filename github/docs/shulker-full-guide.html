The one-sentence pitch Shulker scans web APIs for authorization flaws the way attackers actually exploit them — it takes a valid low-privilege credential and proves with reproducible HTTP evidence whether it can read another user's data, reach admin functions, or extract hidden fields — using AI only for hypotheses and deterministic code for verdicts.

Part 1 · Security theory you must know

1.1 What an API is, and why it is the new attack surface

An API (Application Programming Interface) is a contract that lets machines talk: clients send HTTP requests like GET /users/42 and receive structured JSON. Modern apps are hybrids of many APIs — mobile apps, SPAs, partner integrations, microservices. Unlike a website, an API has no UI to hide behind: every capability the frontend uses is directly callable by anyone with the URL and a credential. The frontend is not a security boundary; the server is.

1.2 Authentication ≠ Authorization (the core distinction)

Authentication (AuthN)Authorization (AuthZ)
QuestionWho are you?May you do this?
MechanismPassword, API key, JWT, OAuth tokenOwnership checks, role checks, ACLs
Failure classCredential theft, token leakageBOLA, BFLA — the classes Shulker detects

The breach pattern that powers this whole project: attackers rarely break cryptography. They authenticate successfully as a normal user, then exploit missing authorization — reading object IDs that belong to someone else, or calling admin functions the UI never showed them. Authentication says "this is Alice"; authorization was supposed to say "Alice may only see Alice's invoices" — and often nobody implemented that second check server-side.

1.3 The vulnerability classes Shulker detects

ClassOWASPDefinitionConcrete attack
BOLA — Broken Object-Level AuthorizationAPI1:2023The server does not verify that the requested object belongs to the caller.GET /vehicles/101 → own car, 200. GET /vehicles/102 → someone else's car, also 200. Attackers enumerate IDs and scrape every user's data (aka IDOR).
BFLA — Broken Function-Level AuthorizationAPI5:2023Privileged functions are reachable by non-privileged callers.PATCH /users/42/role {"role":"admin"} sent as a normal user — the admin panel was hidden in the UI, but the server never checked the role.
Excessive Data ExposureAPI3:2023Responses return more fields than the client needs — full DB rows including sensitive ones.GET /users/42 returns passwordHash, internal flags. The mobile app "never shows" them — attackers read raw HTTP.
Weak Rate LimitingAPI4:2023No throttling on sensitive operations.Unlimited login attempts → credential stuffing; unlimited ID probes → BOLA at industrial scale; OTP brute-force.
Security Controls (positive)—Checks that pass: the server does enforce the rule.Admin endpoint returns 403 for regular users → recorded as PASS, giving defenders an attested baseline.

1.4 Supporting theory used in the build

  • JWT (JSON Web Token) — signed token of form header.payload.signature. Carries identity claims; the scanner extracts it at login and replays it as Authorization: Bearer …. Its recognizable shape (eyJ…) is also what the redaction engine hunts for.
  • API keys — static per-client secrets in a header (x-api-key, x-goog-api-key). Simpler than JWT but long-lived — leakage is high-impact, hence redaction and header-based injection in Shulker.
  • OpenAPI 3.0.3 — machine-readable API contract: paths, operations, parameters, components.securitySchemes. Shulker's parser derives endpoints and expected response schemas from it (the schema is the baseline for exposure detection).
  • Redaction — replacing secrets with <REDACTED> before persistence. A scanner stores evidence; if it stored raw tokens it would itself become a breach vector.
  • Rate limiting — server-side throttling (429 Too Many Requests). Detected politely: Shulker sends a bounded probe burst and observes.
  • IDOR — Insecure Direct Object Reference, the classic pre-2023 name for BOLA.

Part 2 · The stack — every technology and why

2.1 Monorepo layout (npm workspaces)

shulker/
├── apps/
│   ├── sandbox/       ShulkerLab — deliberately vulnerable demo API (port 8700)
│   ├── scan-api/      Backend: REST + SSE, scan orchestration, reports (port 8600)
│   ├── web/           React + Vite operator dashboard (port 5173)
│   └── cli/           `shulker scan` — same engine, CI gate with --fail-on
├── packages/
│   ├── scanner-core/  Scan engine, SafeHttpClient, detectors, AI module, parser
│   └── shared/        Types, severity ordering, redaction engine
├── scripts/           dev.sh · e2e.mjs (60 checks) · verify-demo.mjs
└── data/              SQLite DB + generated reports

Why a monorepo? One repo, one `npm install`, one `npm run dev` — critical for a hackathon demo. Workspaces give each package its own package.json while sharing a single lockfile and node_modules, and shared types flow between engine, server and UI with zero publish steps.

2.2 Technology choices and their reasons

2.3 Why this stack wins a hackathon demo

  • npm install && npm run dev → everything up in ~10 seconds, no services.
  • No API keys required to demo (AI is optional; deterministic rules run without Gemini).
  • Works fully offline except AI hypotheses and external-target scans.

2.4 The safety architecture (what makes it a responsible scanner)

GuardMechanism

Response caps512 KB streaming truncation — no unbounded memory.
No redirectsredirect: 'manual' — evidence reflects the real first response.

Part 3 · Inside the scanner

3.1 Scan lifecycle (engine phases)

POST /api/scan ─▶ validateTarget + confirmAuthorized + buildAuthHeaders └▶ ScanEngine.run(): parse Parse OpenAPI/Postman/HAR → endpoints + auth + schemas authenticate Login actors (Alice/Bob) OR static credentials (API key/bearer) hypotheses Resource/ownership discovery → AI hypotheses (optional) testing BOLA · BFLA · Exposure · Rate-limit detectors (bounded) findings Correlate, dedupe, assign severity + reason done Persist result, emit SSE SCAN_DONE, reports on demand

3.2 SafeHttpClient — the single HTTP chokepoint

Every request the scanner makes passes through one class that enforces timeout, size cap, no-redirect and redaction of anything stored. defaultHeaders injects user static credentials once so every detector inherits the auth context automatically. This chokepoint is why budget and safety guarantees are enforceable at all — there is no side door around it.

3.3 How each detector works (the real logic)

DetectorProcedureVerdict rule
BOLA1. Discover list endpoints and object ids per actor. 2. Record which objects belong to Alice. 3. Replay Alice's read/update requests using Bob's token on Alice's object ids.200/OK with the other actor's token → confirmed, with both responses as evidence and a curl PoC.
BFLAIdentify privileged operations (admin paths, role-mutating writes). Call them as a regular user, and with tampered role claims.Success status as non-admin → confirmed (CRITICAL if role escalation). 403 → recorded as passing control.
ExposureDiff actual response JSON fields against the OpenAPI schema for the operation; scan for sensitive patterns (passwordHash, tokens, PII names).Sensitive undocumented field present → confirmed HIGH with the offending payload as evidence.
Rate limitSend ≤ 25 rapid, polite probes at one sensitive endpoint (e.g. login). Observe statuses, headers (RateLimit-*), latency trends.No 429 / no backoff signal across the burst → potential MEDIUM (deliberately conservative).

3.4 Severity: deterministic, explainable

Findings carry severity + severityReason computed by rules (type × confirmability × sensitivity of leaked field × privilege gained), never by the LLM. CI users can gate with shulker scan --fail-on high and trust exit codes.

3.5 AI + deterministic verification (the flagship idea)

Why the AI never has the final say LLMs hallucinate; a vulnerability scanner that reports hallucinated findings is worse than useless. Shulker's division of labor: Gemini reads the spec and ranks which endpoints/objects look juicy (hypotheses, prioritization); code then tries each hypothesis with real HTTP and either produces evidence or drops it. Result: zero hallucinated findings, by construction. Without a Gemini key the scanner still runs fully on deterministic rules.

3.6 Contract discovery & templates

  • Imports — OpenAPI (JSON/YAML), Postman Collections, HAR files, manual entry, spec-by-URL — all parsed into one endpoint model with auth classification.
  • Quick API Templates — one click for Gemini / OpenAI / GitHub / Stripe generates a valid OpenAPI 3.0.3 spec in memory, auto-fills target + auth (e.g. Gemini → x-goog-api-key), and shows a view/copy/download preview. No file wrangling in the demo.

4.3 External authorized mode

  • Toggle Allow External Targets + per-scan authorization checkbox → public HTTPS targets and public spec URLs accepted.
  • Static auth: API key (custom header name), Bearer, Basic — injected into every request, redacted everywhere.
  • Live-verified against the public Swagger Petstore: 19 endpoints discovered, 8 tested, API key never stored in plaintext.
  • Templates make the flow file-less: pick provider → key from provider console → scan.

Part 5 · Quality, bugs & verification story

5.1 The test gate (run after every change)

1. npx tsc --noEmit (web · scan-api · scanner-core) 2. npx vite build 3. node scripts/e2e.mjs 60 checks: [1] full sandbox scan (endpoints, tests, BOLA/BFLA/exposure confirmed) [2] redaction sweeps (no raw JWT / password hashes anywhere) [3] reports (markdown + html, contain PoC, leak-free) [4] authorization matrix (external refuse/allow, Host-injection blocked, api-key/bearer/basic/custom header building) [5] template matrix (4 templates: valid 3.0.3, validator-pass, auth-marked) 4. node scripts/verify-demo.mjs live HTTP against a freshly booted server

5.3 Verification philosophy

  • Trust nothing ambient — every check boots what it needs and asserts on real output.
  • Security claims need sweeps — "redaction works" is a regex sweep over the entire serialized scan result, not a hope.
  • Matrix-test the gates — authorization logic is exactly where you test both the allow and the refuse path.
  • Green means re-runnable — the whole gate is two commands anyone can run before judging.
Cheat sheet: 30-second answers for judges Q: Why not just ask an LLM to find vulns? Hallucination — verdicts need proof; AI only prioritizes.
Q: Is the scanner dangerous? No — budgets, timeouts, redaction, three consent gates, local-by-default.
Q: Why zero dependencies? Supply-chain trust; everything is auditable; SQLite is built into Node.
Q: Does it work without AI? Yes — deterministic rules are the default; Gemini is optional acceleration.
Q: Real APIs? Yes — external mode with static auth, live-verified on Swagger Petstore.
